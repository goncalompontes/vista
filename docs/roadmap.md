## M1 — existing-window video proof of concept

- [ ] Verify actual xdg-desktop-portal consented per-window capture on Niri (portal source flags alone do not prove it). An opt-in `capture-output --confirm` fallback now captures the entire active output through grim/wlr-screencopy, encodes one real 1920x1080 frame and decodes it (118,845 encoded / 8,294,400 decoded bytes in one run), but this is full-output wlr-screencopy, not portal per-window capture, and it cannot close the consent/window-isolation criterion. A `pipewire-loopback --json` diagnostic now verifies a local synthetic PipeWire node through the same `pipewiresrc` RGBA caps/bounds path (5 frames / 1,152,000 bytes at 320x180 in one run) without portal consent or user content; it does not satisfy the per-window portal criterion. A `capture-consent --confirm` diagnostic now negotiates an opt-in *window-only* ScreenCast session and reports PipeWire node IDs, without accessing frames; live consent/stream verification is pending.
- [ ] Implement explicitly consented PipeWire capture and frame lifecycle. Bounded single-frame and eight-frame GStreamer diagnostics have synthetic frame, partial-sequence timeout, and cleanup tests. Both readers now validate RGBA caps, dimensions, and frame-buffer bounds, including negative tests. Burst reads distinguish a terminated stream from a silent timeout and test cleanup in both cases. A three-second/120-frame aggregate-only capture monitor now exercises a longer-lived capture lifecycle with bounded AppSink buffering; synthetic EOS, timeout, invalid-cap and frame-limit tests verify shutdown. Manual desktop/portal verification and an indefinite streaming lifecycle are pending.
- [ ] Encode frames and show a locally decoded test stream with latency measurements. H.264 factory discovery and a bounded synthetic encode/decode CLI now exist; codec-test verifies actual compressed and decompressed samples without desktop capture. A separate `bridge-test --json` diagnostic now transfers eight synthetic RGBA frames through the permission-scoped `StreamSession` queue into a real GStreamer H.264 AppSrc encoder; NVIDIA hardware integration passed. The opt-in `capture-h264 --confirm` diagnostic now wires an explicitly portal-granted single window through the restricted PipeWire stream and bounded session into an in-memory H.264 encoder, with closure detection and bounded termination. Synthetic tests exercise the same worker boundary, fault injection, and prompt cancellation of a stalled source, with pipeline cleanup assertions. The diagnostic inspects both GStreamer pipeline buses for asynchronous source/encoder errors instead of reporting all failures as timeouts, and prioritizes portal closure over a simultaneously ready worker result. Actual Niri window-to-H.264 output and interactive revocation still require manually approved verification. The separate `bridge-test` uses synthetic authorization; `capture-h264` requires an actual portal window grant but has not yet been tested against an approved chooser. A new `sync-test --json` diagnostic closes the local loop from synthetic RGBA through the permission-scoped queue, the real H.264 encoder, the decoder-resynchronization gate and a real H.264 decoder, injecting one loss and verifying suppressed deltas plus recovery; after the loss the consumer requests a keyframe and the producer restarts the encoder to produce a fresh SPS/PPS IDR rather than waiting for a periodic GOP (one run: 1 request, 1 restart); a paired test also confirms the no-restart variant cannot recover with the same long GOP (PR #15). It reports in-process encode→decode traversal latency, not capture or network latency. Every emitted access unit now also crosses a ChaCha20-Poly1305 media record over a localhost TCP loopback (one run: 11 records / 60,473 ciphertext bytes, 60,297 plaintext) before decoding; the record layer rejects plaintext above 64 KiB. This verifies an encrypted media hop in the same process, not a remote client, WebRTC transport or a real pairing. None of these prove live capture latency or iOS playback.
- [ ] Handle window removal, resize, occlusion and permissions safely. A pure host-side stream-session guard now enforces explicit authorization, token invalidation on revocation, terminal shutdown, bounded two-frame latest-first backpressure, resolution-change queue flushing and strict RGBA geometry validation, with unit tests. The bounded diagnostic now connects this guard to the portal/PipeWire worker, and a portal `Closed` notification cancels capture. Continuous streaming, complete compositor/window disappearance handling, and interactive revocation verification remain pending.

The host now also has a **transport-neutral, permission-scoped H.264 access-unit handoff**: a two-unit bounded queue, 16 MiB maximum per unit, presentation timestamp/keyframe metadata, oldest-unit drop counters, resize flushing, and revocation invalidation. The live capture-to-encoder diagnostic fills and drains this in-memory handoff; it does **not** send bytes to a client. The encoded sink explicitly negotiates Annex-B byte-stream H.264 with AU alignment. The new transport-neutral `H264SyncGate` now signals explicit decoder discontinuities for startup, encoded-queue overflow, resize, GStreamer `DISCONT`, consumer resets/reconnects, invalid bitstream headers and conservative codec-configuration changes, suppressing delta units until an SPS/PPS-prefixed IDR. The live H.264 parser is configured to repeat parameter sets at IDR and its encoded AppSink uses backpressure rather than silent drop. This is NAL-header recovery gating, **not** full H.264 validation, automatic IDR requests, detection of every upstream loss, or an authenticated streaming client; future producers/transport must signal any additional losses and request recovery keyframes as needed. Authenticated network transport remains separate. Unit tests and the ignored synthetic live-worker test cover this boundary. No real Niri capture or remote playback is claimed.

## M2 — secure remote session

- [ ] Host-client authenticated pairing and session state machine. A versioned, transport-neutral control-frame codec and state machine now exist (`host/src/protocol.rs`, `protocol-test`) with HMAC-SHA256 confirmation, HKDF session keys, version negotiation, strict sequencing, offer expiry and deny-by-default permissions; negative tests cover wrong secrets, replay/order, expiry, permission escalation and version mismatch, and Swift-compatible JSON fixtures exist. A backend-agnostic capability/action/portable-input contract (`host/src/capability.rs`, `capability-test`) now defines target/grant/revision freshness, bounded parameter schemas, action results, menu trees and held-input cleanup, with Rust and Swift-compatible fixtures; no client UI wiring or native injection exists yet. No listener, discovery, TLS/QUIC/WebRTC transport, frame encryption, host identity signature or iOS integration yet; the PSK design has no forward secrecy.
- [ ] Low-latency encrypted transport and reconnect/backpressure. A bounded ChaCha20-Poly1305 control-record layer now encrypts frames after pairing, using implicit per-direction nonce counters and session/direction AAD; tamper, replay and wrong-direction records are rejected, a localhost-only `protocol-loopback` diagnostic exercises the full pairing plus encrypted SessionOpen/KeyframeRequest/Ping over a real TCP socket, and a one-shot `protocol-serve`/`protocol-client` pair performs the same exchange across two processes. No production listener, TLS/QUIC/WebRTC, discovery, metadata protection, congestion control, reconnect/backpressure handling or media transport yet.
- [ ] Input translation: pointer, touch gestures, keyboard and modifiers. Portable absolute/relative pointer, button, scroll, physical-key and committed-text events plus release-all cleanup are modelled and tested in `host/src/capability.rs`; no native injection or gesture-binding UI is implemented.
- [ ] Per-stream permissions and revoke mechanism.
